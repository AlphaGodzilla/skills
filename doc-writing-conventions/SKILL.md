# 文档行文规范（skill / AGENTS.md / ADR）

## 一、先看全局

你写的文档，读者只有两个动作：判断**要不要照做**，以及照做时**每一步做什么**。本规范用两类约束保证这两个动作不发生偏差：

- **结构约束**决定信息出现的顺序：开篇给图景，再给骨架，最后给细节。
- **语言约束**决定单个句子能否被唯一理解：优先中文、删冗余、消除分词歧义。

全文结构：本图景 → 两条总原则 → 六条硬规则 → 写作流程 → 三类文档的差异 → 自检清单。可直接套用的文档骨架见 `references/templates.md`。

读完本规范后应能直接动笔，不需要再问"这段该怎么组织"。

### 适用与不适用

适用：

- 新建或修改 skill 的 `SKILL.md` 及其 references 文件
- 新建或修改 `AGENTS.md`、`CLAUDE.md` 等代理指令文件
- 新建或修改 ADR（架构决策记录）

不适用：

- 代码注释与 API 文档：跟随语言与工具链惯例
- 面向外部用户的 README 与教程：需要叙事，可以放宽精简要求
- 项目已有明确风格时：**沿用项目既有风格**，只治理歧义句

### 两条总原则

1. **为读者的一次通读负责**：读者只读一遍就要正确行动，不能依赖回读或猜测。
2. **改动最小**：修改既有文档时先保留原有结构、编号与术语；只补信息、只改歧义句。

## 二、六条硬规则

### R1 开篇先给图景

文档首段回答四个问题，缺一不可：**给谁读**、**解决什么问题**、**读完能做什么**、**全文有哪几块**。四问控制在 3～5 句，然后才进入细节。

- 反面：直接以"## 背景""## 术语定义"开篇，读者读了三节仍不知道文档的用途。
- 正面：`本规范规定提交信息的格式。读者是提交代码的人与模型。读完能写出符合仓库风格的提交信息。全文分：格式、类型表、正文写法、示例。`

### R2 由浅入深，先骨架后细节

按"概念 → 用法 → 边界 → 来历"排列。写之前先只写标题，检查顺序；每个章节的第一句先给结论，后续句子才给理由与例外。

- 禁止细节早于概念：任何术语在定义之前不得使用。
- 允许前向引用（"详见 §5"），禁止反向依赖（读者必须记住后文才能理解前文）。
- 同级标题必须同构：同为名词短语，粒度相当。禁止出现"其他""杂项""补充"这类无信息标题。

### R3 选对结构容器

| 内容形态 | 容器 |
| --- | --- |
| 一个判断加理由 | 段落，不用列表 |
| 3 条以上并列要求、或需要逐条核对 | 列表 |
| 二维对照（条件→行为、反例→正例） | 表格 |
| 有层级且有先后 | 编号章节 + 标题 |
| 需要原样复制的内容（路径、命令、模板） | 代码块 |

列表项必须能独立读懂：禁止"同上""如前"开头的列表项。

### R4 精简等于删冗余，不等于删信息

删除以下五类内容：开场铺垫（"在当今快速迭代的背景下"）、同义重复（"非常重要且关键"）、读者可自行推断的常识、自我评价（"本规范严格遵循最佳实践"）、无法验证的承诺（"显著提升效率"）。

必须保留以下四类内容：触发条件、可验证的阈值与例外、反例（说明错误做法）、验收判据。

**删句判据**：删掉这句话后，读者是否会做错事或多问一次？会，则保留；不会，则删。

### R5 中文优先，术语保留原形

- 叙述、标题、注释、提交信息一律用中文。
- 例外：ADR 的章节标题保留 MADR 英文原名（如 `Context and Problem Statement`），正文与列表内容仍用简体中文；骨架见 `references/templates.md` 第三节。
- 专有名词、命令、标识符、代码保留原文：写 `git commit --amend`，不写"追加提交命令"。
- 首次出现的英文术语按 `中文（English）` 形式给出，之后全文只用一种写法。
- 同一概念全文只用一个词：不得"模块/组件/服务"混指同一事物。

### R6 消除分词歧义

中文无词间空格，歧义集中在名词堆叠与悬空指代。逐句检查下表五类：

| 歧义类型 | 坏例 | 改法 |
| --- | --- | --- |
| 名词堆叠（三个以上名词连用，分词边界不定） | 项目配置文件解析逻辑修改说明 | 修改项目配置文件的解析逻辑：说明 / 拆成两句 |
| 动宾与偏正两可 | 支持离线模式的数据同步 | 在离线模式下支持数据同步 |
| 悬空指代 | 该方案、上述内容、相关配置 | 重复具体名词；首次出现用全名，后续可用已定义的简称 |
| 并列层次不明 | 前端 后端 和 数据库 | 前端、后端与数据库；或用列表逐项列出 |
| 双重否定与万能动词 | 不可不执行、进行处理、加以实现 | 必须执行、执行、实现 |

补充两条可验证性要求：

- 程度词换成阈值：不写"尽量少用""部分场景"，写"不超过 3 个""当输入为空时"。
- 情态词只用三个：**必须**、**应当**、**禁止**。禁止使用"建议""最好""可以考虑"表达硬性要求。

## 三、写作流程

1. **定图景**：写下读者、目的、读完能做什么、全文分几块。这四行直接成为首段。
2. **列骨架**：只写标题，不写正文；检查同级标题同构、顺序为由浅入深。
3. **逐节展开**：每节先写结论句，再补条件、例外、示例；一次只写一节，写完即检。
4. **通读找歧义**：按 R6 的表逐句扫描，重点看名词堆叠句与含"该/上述/相关"的句子。
5. **跑自检清单**：见第五节。修改既有文档时，额外确认结构与编号未被破坏。

## 四、三类文档的差异

| 文档 | 读者 | 首要目标 | 必备节 | 篇幅倾向 |
| --- | --- | --- | --- | --- |
| `SKILL.md` | 模型 | 让模型能直接执行动作 | 触发/不触发、原则、流程、自检 | 主文件精简，长清单与模板下沉到 references/ |
| `AGENTS.md` | 模型与人 | 约束行为边界 | 铁律（必须/禁止）、决策优先级、外部资料指向 | 极简，只写约束，不写教程 |
| ADR | 未来的人与模型 | 保存决策理由与代价 | frontmatter `status`/`date`、Context and Problem Statement、Decision Outcome、Consequences（其余 MADR 元素可选） | 一页，历史条目只增不删 |

三者的通用规则：**结论在前，理由在后**；被否决的方案必须留名并写明否决理由，否则读者会重新提议它。

可套用的骨架见 `references/templates.md`。

## 五、自检清单

- [ ] 首段回答四问：给谁读、解决什么问题、读完能做什么、全文有哪几块
- [ ] 所有标题为名词短语，同级同构，无"其他/杂项"
- [ ] 每个术语在首次使用之前已定义，全文写法唯一
- [ ] 每个"该/上述/相关/其"都能对应到唯一的具体名词
- [ ] 无三个以上名词连用而不加标点或虚词
- [ ] 无"进行/实现/进行处理/相关/尽量/部分"等空转或模糊表述
- [ ] 所有要求可验证：给出阈值、条件或布尔判断
- [ ] 硬性要求只用"必须/应当/禁止"表达
- [ ] 反例与正例成对出现，读者能对照判断
- [ ] 删除任意一句，读者都不会因此做错事
- [ ] 修改既有文档时，原结构、原编号、原术语未被打乱
