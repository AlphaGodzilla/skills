# 文档行文规范

本规范面向撰写或修改文档与代码注释的人和模型，解决适用范围不清、内容过时和表述歧义的问题。读完后应能判断文档类型、核实事实、组织内容并完成自检。全文分为适用范围、内容铁律、行文规则、写作流程与自检；skill 和代理指令文件的骨架见 `references/templates.md`，ADR 的格式与维护流程交由 skill `adr-writing`。

## 一、适用范围

内容约束与行文风格必须分开判断：项目既有风格不改变内容铁律的适用范围。

| 对象 | 行文规则 R1～R6 | 当前状态铁律 R7 |
| --- | --- | --- |
| skill 的 `SKILL.md` 及其 references、`AGENTS.md`、`CLAUDE.md` | 按本规范执行；已有明确风格时保留有效风格，治理歧义 | 非日志记录类内容适用 |
| ADR | 按 `adr-writing` 的模板与专项规则执行，正文遵守本规范的清晰、精简与中文要求 | 不适用 |
| 其他日志记录类文档 | 沿用对应文档规范或项目风格 | 不适用 |
| README、教程、API 文档等其他文档 | 沿用项目风格与工具链惯例，不强制套用本规范的骨架 | 非日志记录类内容适用 |
| 代码注释 | 沿用项目与语言惯例，不套用文档骨架 | 适用 |

日志记录类文档用于保存事件或决策发生时的背景、过程与结果；ADR 属于此类文档。必须按文档用途分类，禁止仅凭文件名、时间戳或“历史”章节标题判定豁免。

**禁止在同一文档中混写当前状态说明与历史日志。**需要两类内容时，必须分别存放，并用链接关联。遇到既有混合文档或无法确定文档类型时，必须先向用户确认分类与拆分方案，禁止自行删除历史内容或将整份文件判为豁免。日志中描述事件发生时的状态，属于历史背景，不属于当前状态说明。

### 通用原则

1. **为读者的一次通读负责**：读者必须能正确理解信息或执行要求，不依赖猜测；历史记录必须能说明当时发生了什么及其依据。
2. **事实不编造**：禁止虚构事实、数据、阈值、决策或历史讨论；依据不足时必须先确认，日志记录中的未确认信息按对应专项规范处理。

## 二、内容铁律

### R7 只描述当前状态，不记录 AI 历史修改过程

除所有日志记录类文档外，文档与代码注释必须描述当前状态，禁止记录 AI 历史修改记录。必须按代码和项目现状更新内容，禁止将尚未确认的实现偏差写成新的业务规则。

- **临时阶段不入文档**：某次开发任务临时划分为 `phase1`～`phase5` 时，禁止在非日志记录类文档与代码注释中保留这些阶段标签、相关字段描述或推进记录；必须直接描述当前功能、结构与行为。
- **失效决策不留历史**：决策 A 已作废、决策 B 已确认为当前决策时，必须只记录 B 及其理由与约束，禁止保留 A 的历史描述或从 A 改为 B 的修改过程。
- **实现偏差不改业务规则**：代码与已确认规则不一致时，必须指出具体差异及依据，向用户确认；确认前禁止仅凭实现改写业务规则。
- **决策确认不等于实现完成**：已确认决策尚未落实时，必须区分当前实现与已确认决策，禁止将决策描述为已实现状态。

**所有日志记录类文档均不受 R7 约束。**ADR 必须记录技术决策发生时的前因后果；禁止为了只呈现当前状态而删除或改写日志中的历史事实。ADR 的格式、元数据、状态流转与历史维护只按 `adr-writing` 执行，本 skill 不维护第二套规则。

## 三、行文规则

### R1 开篇交代用途

开篇必须让读者知道文档的读者、目的与用途；内容较多时还必须给出结构导航。按文档类型组织，不强制固定句数。

- skill：交代给谁用、解决什么问题、读完能做什么及全文结构。
- 代理指令文件：交代约束谁、在哪些工作中生效，随后直接给出约束。
- ADR：按 `adr-writing` 的模板交代决策当时的问题与背景，禁止额外强加通用说明文的开篇骨架。

反例：skill 直接进入操作细节，读者不知道何时使用。正例：`本 skill 帮助模型检查提交信息。修改或创建提交时使用。读完能判断格式是否合规，全文分为格式、示例与自检。`

### R2 先骨架，后细节

先确定标题，再展开正文；依赖概念的细节必须出现在必要说明之后。章节先给结论或动作，再补条件、理由与例外；ADR 的章节顺序遵循专项模板。

- 标题必须准确概括内容，同级标题粒度一致；名词短语与动作短语均适用，禁止使用无具体含义的“其他”“杂项”“补充”。
- 专业缩写与项目特有概念必须在首次需要理解时解释；通用词语不重复定义。
- 前向引用必须仅用于补充细节，禁止让读者依赖后文才能理解当前要求。

### R3 按内容选择结构

| 内容形态 | 容器 |
| --- | --- |
| 一个判断及其理由 | 段落 |
| 并列要求或逐条核对项 | 列表 |
| 有先后关系的操作 | 编号步骤 |
| 条件与行为、反例与正例等二维对照 | 表格 |
| 层级内容 | 标题与子标题 |
| 需要原样复制的命令、代码或模板 | 代码块 |

列表项必须能独立读懂，禁止用“同上”或“如前”代替具体对象与动作。

### R4 精简冗余，保留必要信息

删除开场铺垫、同义重复、无助于理解的常识、自我评价与无法验证的承诺。必须保留影响理解、执行或核验的条件、例外、理由、示例与验收判据；日志中的历史事实不按“是否仍有效”筛除。

**删句判据**：删除后会让读者理解错误、执行错误或缺少核验依据，则保留；没有这些影响的冗余句应当删除。示例用于说明易错边界，禁止为凑反例与正例而重复正文。

### R5 中文叙述，原样保留标识符

在本规范的行文适用范围内，标题与叙述使用简体中文；专有名词、路径、命令、标识符与代码保留原文。代码注释和其他文档的语言沿用项目惯例，提交信息不由本 skill 规定。

- ADR 章节标题按 `adr-writing` 和项目模板执行，不在本 skill 中重定义。
- 需要解释的英文术语，首次出现时给出中文释义，之后统一写法；禁止给命令与代码标识符强行添加中文译名。
- 同一概念必须统一用词，禁止将不同的模块、组件或服务混称为同一对象。

### R6 按语义消除歧义

逐句检查名词堆叠、悬空指代、并列层次与空转用词。判据是读者能否唯一理解含义，不是是否出现某个词。

| 问题 | 反例 | 正例 |
| --- | --- | --- |
| 名词堆叠 | 项目配置文件解析逻辑修改说明 | 项目配置文件解析逻辑的修改说明 |
| 动宾与偏正两可 | 支持离线模式的数据同步 | 在离线模式下支持数据同步 |
| 指代无唯一对象 | 该方案负责校验 | 请求校验器负责校验 |
| 并列层次不明 | 前端 后端 和 数据库 | 前端、后端与数据库 |
| 空转动词 | 对空请求进行相关处理 | 拒绝空请求 |

- “该”“相关”“实现”等词只有在指代不明或不增加信息时才需改写，禁止机械禁词。
- 硬性要求使用“必须”或“禁止”；非强制要求必须明确其条件或适用边界，禁止用“建议”“最好”掩盖硬性约束。
- 有真实阈值时写阈值，没有阈值时写明确条件或可判定结果，禁止为了可验证而编造数值。

## 四、写作流程

1. **分类与定范围**：判断是现状说明还是日志记录，按第一节选择行文规则；混合文档先确认拆分方案。ADR 同时读取 `adr-writing`，本规范只负责行文与内容边界，不代替其专项流程。
2. **核实依据**：查看任务涉及的代码、项目现状与已确认决策；日志查看事件或决策当时的证据。区分已实现行为、已确认但未实现的决策与未确认偏差，发现差异先确认。
3. **确定用途与骨架**：按文档类型交代用途，只列标题并检查层级；仅按需读取 `references/templates.md` 的对应骨架。
4. **展开与更新**：写结论、条件、理由与必要示例；修改现状文档时同步清理过时描述，日志记录按专项维护规则处理。
5. **通读与自检**：检查语义、引用和适用的自检项；修改主文件规则时同步检查 references，禁止主文件与模板保留两套冲突要求。

## 五、自检

### 所有适用文档

- [ ] 文档用途与类型明确，无现状说明与历史日志混写；类型或拆分方案不明确时已向用户确认
- [ ] 开篇符合文档类型，标题准确且层级一致，必要概念已解释
- [ ] 指代与并列关系明确，用词统一，无机械禁词或为满足格式而添加的冗余内容
- [ ] 每句话均提供必要信息，删除后不影响理解、执行或核验的冗余句已移除
- [ ] 事实与决策有依据，要求有明确对象、条件或可核验结果，无编造阈值
- [ ] 主文件与 references 的规则一致，无冲突或失效引用

### 非日志记录类文档与代码注释

- [ ] 只描述当前状态，无 AI 历史修改记录、临时开发阶段记录或已作废决策的历史描述
- [ ] 当前实现与已确认决策已区分，未把待实现决策写成已实现行为
- [ ] 实现与已确认规则有差异时已确认，未将未经确认的偏差写成业务规则

### 日志记录类文档

- [ ] 保留事件或决策发生时的背景、过程与结果，未为符合 R7 而删除或改写历史事实
- [ ] 未混入用于指导当前使用的现状说明；需要关联时链接独立文档
- [ ] ADR 的格式、元数据与历史维护已按 `adr-writing` 检查
