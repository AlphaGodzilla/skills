# 三类文档的可套用骨架

本文件给出 `SKILL.md`、`AGENTS.md`、ADR 三类文档的骨架。用法：`SKILL.md` 与 `AGENTS.md` 先复制骨架的全部标题，再按 `SKILL.md` 中的 R1～R6 填写正文；ADR 直接复制第三节的 MADR 模板文件，按模板首行说明删除说明块。骨架中的方括号与花括号均为待替换项，不要原样保留。

## 一、SKILL.md 骨架

```markdown
---
name: <kebab-case，与目录名一致>
description: <做什么 + 何时适用。写清触发场景与关键词，模型按此决定是否加载本 skill。>
---

# <skill 名>

## 做什么

<三到五句：给谁用、解决什么问题、读完能做什么、全文有哪几节。>

## 何时适用 / 何时不适用

适用：
- <触发场景一，含用户可能说出的原话或关键词>
- <触发场景二>

不适用：
- <易混淆的相邻任务>：改用 <替代 skill 或做法>

## 原则

1. **<原则名>**：<一到两句可执行的约束>
2. **<原则名>**：<...>

## 流程

1. **<步骤名>**：<输入来自哪里、执行什么、产出什么>
2. **<步骤名>**：<...>

## 自检

- [ ] <可判定的验收项>
- [ ] <可判定的验收项>
```

下沉规则：单节超过约 40 行，或整篇超过约 200 行时，把长表格、模板、清单移入 `references/<主题>.md`，并在原处留一行指向该文件的相对路径。

不写进 `SKILL.md` 的内容：原理推导（放 references）、与本任务无关的背景、其他 skill 已覆盖的流程（改为一行指向该 skill）。

## 二、AGENTS.md 骨架

```markdown
# <项目名>：代理指令

<一到两句：本文件约束谁、在哪些工作下生效。>

## 铁律

- 禁止 <具体行为>；原因是 <代价>。
- 必须 <具体行为>。
- 遇到 <不确定条件> 时，停下并向用户提问，不得自行假设。

## 决策优先级

冲突时按以下顺序裁决，序号小者优先：

1. <最高优先级来源，例如技术最优>
2. <次高优先级来源，例如项目既有约定>
3. <再次，例如用户临时要求>

## 需要查阅的资料

- <主题关键词> → 读取 `<相对路径或 skill 名>`
- <主题关键词> → 读取 `<...>`

## <可选>项目约定

- <语言与命名><...>
```

约束写法：每条铁律必须包含**禁止或必须**、**具体对象**、**违反后的代价**。只写代价不明的要求会造成两种后果：模型忽略它，或过度使用它。

禁止写进 `AGENTS.md` 的内容：教程与背景介绍、可由工具链自动执行的格式规则（交给 linter）、与代码重复的说明。

## 三、ADR 模板（MADR 4.0.0）

```markdown
---
# 可选元数据，按需保留
status: "{proposed | rejected | accepted | deprecated | superseded by ADR-0123}"
date: {YYYY-MM-DD，决策最后一次更新的日期}
decision-makers: {参与决策的人；AI 助手不得写入自己}
consulted: {征求意见的对象}
informed: {仅被告知进展的对象}
---

# {简短标题：点出「解决的问题」与「找到的方案」}

> **MADR 4.0.0 模板**（<https://github.com/adr/madr/blob/4.0.0/template/adr-template.md>）。
> 用法：复制本文件为 `NNNN-kebab-case-title.md`，**删除本说明块**，按需保留标「可选」的元素。
> 语言约定：正文简体中文，章节标题保留 MADR 英文原名，技术名词保留英文。
> 写之前先调用 skill `adr-writing`，并读 `docs/adr/README.md`。

## Context and Problem Statement

{用两三句话描述上下文与问题，可写成问题句，并链接相关 issue 或讨论记录。交代「为什么现在必须做这个决策」以及影响面（架构的哪一部分）。}

<!-- 可选 -->
## Decision Drivers

* {驱动因素 1：某种力量、关切或约束}
* {驱动因素 2}
* …

## Considered Options

* {方案 1 标题}
* {方案 2 标题}
* {方案 3 标题}

## Decision Outcome

选择「{方案 1 标题}」，因为 {理由：唯一满足某项硬性约束的方案 / 解决了某个驱动因素 / 综合最优（见下）}。

<!-- 可选 -->
### Consequences

* Good, because {正面后果}
* Bad, because {负面后果}

<!-- 可选 -->
### Confirmation

{如何验证决策被落实并被遵守：设计评审、代码评审、ArchUnit 之类的自动检查。}

<!-- 可选 -->
## Pros and Cons of the Options

### {方案 1 标题}

{示例 | 说明 | 更多信息的指针}

* Good, because {论据}
* Neutral, because {不好不坏的论据}
* Bad, because {论据}

### {方案 2 标题}

…（同上）

<!-- 可选 -->
## More Information

{补充证据、团队共识、复查时机、与其它 ADR 的关系。}
```

状态流转：`proposed` → `accepted` → `superseded by ADR-XXXX` 或 `deprecated`；被否决且值得留档的方案记 `rejected`。旧条目只修改 `status` 与 `date` 两个字段，正文不改、不删；决策变更时新写一条，并在新旧两条的 `status` 与 `More Information` 中互相指向。

章节标题例外：ADR 的章节标题使用 MADR 英文原名（如 `Context and Problem Statement`），不改写为中文；正文与列表内容仍用简体中文。

## 四、三类文档的共用填写规则

| 位置 | 规则 |
| --- | --- |
| 标题 | 名词短语；同级标题粒度相当；不新增"其他""杂项"节 |
| 首段 | 回答四问：给谁读、解决什么问题、读完能做什么、全文有哪几块 |
| 每条要求 | 只使用"必须/应当/禁止"表达硬性约束；给出阈值或条件 |
| 举例 | 反例与正例成对出现，先反例后正例 |
| 指代 | 不写"该方案""上述内容""相关配置"；重复具体名词 |
| 路径 | 使用相对路径；提到外部资料时给出可执行的动作（读取哪个文件） |
| 修改既有文档 | 保留原结构、原编号、原术语；只补信息与修歧义 |
