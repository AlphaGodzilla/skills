# 源码逆向本体建模（OMF v6）

本 skill 面向分析已有代码库的模型与工程师，把可证明的实现事实转换为本体模型，并保留不能表达的现状与待确认问题。读完能确定源码范围、沿调用链取证、产出模型、检查追溯与覆盖情况。全文分为适用范围、依赖与口径、约束、执行流程、输出与验收；逐模型取证、输出格式和校验边界分别见下列 references。

## 适用范围

适用：已有源码，要求逆向生成 M1～M7、MM、MI，分析遗留系统、补齐现状模型，或根据源码变更更新已有逆向模型。

不适用：
- 只有业务需求、没有源码：使用 `ontology-modeling` 的需求取证流程。
- 只有 DDL 或接口规格：只能提取这些材料能证明的局部信息；禁止声称已完成全系统逆向。
- 要求目标架构、事件化改造、业务规则设计或代码生成：另开任务，不混入现状模型。

## 依赖与模型口径

上游规范：[ontology_modeling_framework_v6.md](https://github.com/sharptoolbox/ontology_modeling_framework/blob/main/ontology_modeling_framework_v6.md)。OMF 指 Ontology-Driven Software Modeling Framework（本体驱动的软件建模框架）。

本 skill 显式依赖 `ontology-modeling`，必须通过运行时的 skill 定位入口找到其目录，确认以下文件存在并读取所需内容：

| 资源 | 读取时机与用途 |
| --- | --- |
| 本 skill 的 `references/framework-profile.md` | 开始时读取，确定模型职责、文件集合及上游口径冲突的处理方式 |
| `ontology-modeling/SKILL.md` 的「输出目录与版本管理」 | 确认输出位置时读取，复用标准目录、信息包文件名、索引与评审位置 |
| `ontology-modeling/references/model-templates.md` | 序列化模型前读取，复用字段、根键、稳定 ID 与 YAML 骨架 |
| `ontology-modeling/references/reverse-elicitation.md` 第四节 | 组织标准信息包前读取，复用对象卡等文件的内容结构与用户确认状态 |
| `ontology-modeling/references/event-storming-extraction.md` 第九节 | 汇总取证结果时读取，复用 DDD 四张表、取数索引与元素追溯骨架，不照搬需求事件化设计 |

禁止直接套用需求建模 skill 的完整流程：其补全场景、事件解耦及业务追问是正向设计约束，本 skill 的工作是忠实逆向。模板只提供表示方法，示例不是目标项目事实。缺少依赖时必须停止并告知用户，禁止自行生成兼容替代品。

默认交付 **M1～M7、ME、MM、MI 共 10 个 YAML 文件**。ME 是独立事件模型，不包含在 M1～M7 中；M4/M6/MI 的事件引用依赖它。MU 是可选的 UI 模型，只有用户明确纳入范围且有可读取的 UI 源码时提取。没有前端时禁止虚构 MU，也不以 MU 缺失否定后端逆向。

输出默认沿用 `ontology-modeling` 的 `docs/model/` 目录，完整保留 8 个标准 `intake/` 文档、`yaml/`、`reviews/`、`README.md` 与 `CHANGELOG.md`；`diagrams/` 按需。源码证据、覆盖和差异清单只是 `intake/` 下的扩展，不替代标准信息包。详见 `references/output-contract.md`。

## 约束

1. **实现事实与业务意图分开**：源码是实现事实依据，文档、注释、测试只提供线索或交叉核对。用户确认的目标规则不等于已实现；两者冲突时记录差异并询问，禁止改写现状。
2. **禁止以假设补缺口**：字段、聚合边界、生命周期、角色、查询口径或返回规则需要假设才能成立时，必须停下询问。可保存已取证结果与缺口，但未确认信息不得作为后续推理前提或正式模型事实。
3. **只读代码、只写模型**：禁止修改业务源码、DDL、迁移、构建配置、权限策略或测试；禁止运行应用、访问真实数据库、调用外部服务或执行仓库脚本。静态分析足够时不运行测试；需要额外执行证据时先取得单独授权。
4. **限定读取范围**：只读用户授权的源码与声明文件；禁止读取 `.env`、密钥、凭证、真实账户数据、生产数据、主机隐私目录。禁止跟随符号链接或扫描到代码库外。依赖包、构建产物、生成模型不是目标业务源码证据。
5. **不把现状理想化**：同步跨聚合写入不伪装成 ME/M4；没有发布证据不造运行时事件，未看到消费实现不补造消费者；没有审批实现不造审批流；有副作用的判断不伪装成纯 M3 规则。
6. **不得删掉不适配的实现**：能忠实表示的部分进入标准模型，不能表示的原始调用链、数据变化和契约进入差异清单及覆盖清单，并关联源码。禁止为了校验通过而隐藏业务入口、副作用或错误分支。
7. **稳定引用与独立追溯**：跨模型引用使用稳定 ID；证据、置信判断、提取状态和差异保存在 `intake/`，不向 OMF 标准模型添加私有字段。已有 ID 禁止重新编号或复用。
8. **临时文件只放 `/tmp`**：抓取原文、候选表、测试夹具、缓存与机器报告写入 `/tmp`；模型源文件和持久化证据清单写入已确认的目标目录。禁止自动提交、推送、安装到目标项目或修改其 CI。
9. **模型文件正文必须是 YAML 语法**：`yaml/` 下每个 `*.yaml` 的正文必须用块状 YAML 书写，顶层为块状映射；禁止整体写成 JSON 对象或数组。JSON 在语法上属于 YAML 子集，`.yaml` 文件名不使 JSON 正文合规；字段值内部的 YAML flow 写法不受此限制，两个检查脚本都会拒绝顶层首字符为 `{` 或 `[` 的文件。

## 执行流程

### 1. 确认范围与输出位置

先确认代码库根目录、分析的服务/模块、系统边界、业务域名称、输出目录、排除目录及是否提取 MU。用户已提供的参数不重复问；缺少影响执行的参数必须一次分组询问。

默认输出根目录沿用 `ontology-modeling` 的 `docs/model/`，其标准子目录和文件名不得更换；默认位置不是可覆盖既有文件的授权。先检查是否存在需求/目标模型；存在时询问合并还是另存到如 `docs/model-as-is/` 的独立目录。禁止用现状替换目标设计。将确认结果写入 `intake/scope.md`。

记录当前源码快照：Git 提交标识（有 Git 时）、工作区是否有改动、纳入分析文件的 SHA-256。未提交文件也可分析，但证据必须对应当前内容，不能只引用 HEAD。只记录必要的仓库元数据，不读取全局 Git 配置、远程凭证或主机账户配置。

### 2. 建立源码与业务入口清单

按 `references/code-evidence.md` 列出技术栈、模块、服务端入口、命令/定时任务、消息生产消费、持久化声明、鉴权路径、工作流定义和查询导出入口。先列文件名，再读取已确认的安全文件；禁止对仓库无差别全文搜索。

清单必须覆盖框架隐式入口：继承路由、拦截器、全局异常处理、默认鉴权策略、ORM 转换器、共享查询方法。无法解析动态路由、反射、插件或仓库外依赖时登记缺口，不声称已扫描完整。

产出 `intake/repository-map.md`，并把每项业务入口、持久化对象和查询等写入 `reverse-manifest.yaml.coverage`。入口先建账，再提取模型，避免以已生成模型反推“全部已覆盖”。

### 3. 沿实现链取证

沿 `入口 → 授权/校验 → 应用或领域逻辑 → 读写/状态变更 → 事件或外部调用 → 返回/异常映射` 双向追踪。每个结论记录仓库相对路径、符号、行范围和文件哈希；字段与分支不能只凭类名、方法名或注释判断。

建立 `intake/extraction-map.md`，按对象、行为、规则、事件、协同、角色、流程、查询、映射、接口列出候选项与证据。生命周期只有枚举但无迁移路径时，区分“声明状态”与“已证明的迁移”；事务共用不自动等于同一聚合。

从同一批证据同步标准信息包：填 `glossary.md`、`ddd-extraction.md`、`object-cards.md`、`scenario-list.md`、`actor-permission.md` 和 `flow-catalog.md`。DDD 取数索引连接信息包、标准模型 ID 与源码证据；没有实际事件时保留空表和不存在判据，不能从状态变化补造事件表行。复用文档骨架，不按理想边界重划当前代码。

### 4. 解决歧义与表示冲突

将问题写入 `reverse-manifest.yaml.gaps`，引用证据与受影响模型，附具体问题和需要补充的文件或决策，同步到标准 `intake/open-questions.md` 的问题视图；所有问题闭环以同一 GAP ID 为准。依据不足时停下询问，禁止用低置信猜测继续建模。

已证明但不符合 OMF 的结构记为 `OMF_DEVIATION`；无法用标准模型表达的结构记为 `UNREPRESENTABLE`。保留原始现状，不设计未实现的解耦链，不替现有系统增补规则。用户确认“当前源码确实如此”只确认事实，不意味着符合 OMF，也不关闭尚存在的架构偏差。

### 5. 按依赖顺序生成现状模型

从标准信息包和 DDD 取数索引取数，按共享模板依次生成：

`M1 → M5（参与者/角色）→ M3 → M2 → M7 → ME → M5（权限）→ M4 → M6 → MM → MI → 可选 MU`

MM 的物理证据可提前收集，MI 的入口可先建清单；序列化时等待引用的 ID 确定。M2/ME、M2/M7 等双向引用在关联模型落盘后同步核对，不要求草稿中临时建立不存在的占位 ID。

每个文件必须有 `model_type`、`version`、`domain` 和明确列表根键，正文为块状 YAML 映射（禁止整体 JSON 文档）。空模型使用 `[]`，同时在清单注明 `ABSENT` 的搜索范围和判据；“未找到”和“未检查”不能等同。证据不足使用 `PARTIAL` 并关联缺口，禁止用 `ABSENT` 隐藏未完成分析。

为每个根集合条目增加独立追溯记录；关键字段、表达式、授权条件、载荷、查询列、表列和接口分支也必须定位证据。提取结果与源码不一致时修复提取，不修源码。

### 6. 执行三类验收

按 `references/validation.md`：
1. 用附加逆向检查脚本检查兼容目录和非空标准信息包、10/11 模型文件集合、必需根键、证据哈希与行范围、JSON Pointer（字段定位路径）、元素级追溯和覆盖引用。
2. 同一脚本调用现有 `omf_validate.py --strict`，复用通用结构、跨模型引用和镜像字段检查。
3. 人工检查自动工具未覆盖的语义、完整性、MM/MI 字段口径、事件实际存在性和流程图，并逐项记录结果。

校验通过不证明语义正确；退出码 `3` 表示机械检查通过但仍有未闭环缺口，不得宣称完整通过。既有校验器对真实模型误报时登记工具限制并询问，禁止修改事实、关闭检查或换造模型绕过。

### 7. 交付与增量更新

`README.md` 只描述当前范围、源码快照、标准信息包及模型索引、`未开始 / 进行中 / 已交付` 阶段状态、独立的 10/11 模型完整性状态、覆盖情况、开放问题与验收结果。实际语义评审整理到 `reviews/review-{date}.md`；机器报告仍在 `/tmp`。模型变更日志独立存入 `CHANGELOG.md`；首次新建时无需虚构历史。交付时列出输出目录、模型清单、未解决问题及实际运行的检查结果。

增量运行先比较已取证文件与当前内容，再沿调用链和跨模型 ID 分析影响。重新取证后同步模型、Pointer、覆盖与差异清单；发现已删除入口或对象时先处理全部引用。禁止仅重算哈希后继续使用旧结论，禁止重建 ID 掩盖变化。

## 输出与验收

目录与完整清单格式见 `references/output-contract.md`；可复现命令与测试见 `references/validation.md`。本 skill 的机器检查只读源码和产物，不执行业务仓库代码；源码提取由执行本流程的模型或工程师完成，不是正则扫描器自动重建业务语义。

交付前必须确认：
- [ ] 授权范围、系统边界、输出位置与 MU 取舍已确认，既有目标模型未被覆盖
- [ ] 输出保留 `ontology-modeling` 的标准目录、8 个信息包文档、README 阶段状态和评审入口，逆向扩展未替代标准文件
- [ ] 10 个必需模型文件均存在；没有事实的集合为空，且有不存在判据
- [ ] 模型文件正文为块状 YAML，无整体 JSON 文档
- [ ] 每个模型元素和关键字段均有实现或声明证据，文档/测试不是唯一依据
- [ ] 业务入口、对象、规则、事件、权限、流程、查询、映射与接口在覆盖清单中有明确处置
- [ ] 未将同步协作虚构为事件协同，未补造角色、审批、表名、投递保证或接口错误规则
- [ ] M2/M7 一对一、事件生产消费、角色授权、MM 表列与 MI 契约已核对
- [ ] 未知项已提问，开放差异未被标作符合 OMF，自动检查结果与人工门禁分开记录
- [ ] 未读凭证/隐私/生产数据，未改代码/CI，未自动提交；临时产物仅在 `/tmp`
